\begin{abstract}
A codebase starts in a clean ground state $S_0$: modular, tested, documented. Over time it displaces to $S^*$: brittle, undocumented, tightly coupled. This is not laziness or incompetence. It is structural: the cost to add features cleanly exceeds the cost to patch and hack. The system finds a stable ground state and remains there. Technical debt is not debt. It is displacement.
\end{abstract}

\section{The Clean Code Ground State}

When a project begins:
- Every line has a purpose
- Tests cover the logic
- Architecture is clear
- Adding features takes time but is predictable

This is expensive to maintain. Each change risks breaking something.

\section{The Hacked Code Ground State}

Over iterations, a new stable state emerges:
- Features are added by patching
- Tests are skipped when they fail
- Architecture is implicit (in whoever's head built it last)
- Adding features is fast (until it isn't)

This ground state is cheaper to live in—until the cost suddenly spikes.

\section{Why Refactoring Fails}

A team decides to "fix" the codebase. They plan a rewrite. But the current ground state is stable. It has momentum. Every day the system is not refactored, the cost of refactoring increases (more hacks, more workarounds, more people who don't know the original architecture).

The system returns to the hacked state. Not because the team is weak. Because the return to the clean state is more expensive than living with the current problems.

\section{The Displacement Irreversibility}

Once a codebase displaces, returning is nearly impossible without a rewrite. The path back requires:
- Stopping all feature work
- Accepting months of lower velocity
- Rebuilding trust with stakeholders

The cost is prohibitive. The system stays displaced.
